Contribute a package

Packages are folders in the catalog repository. You add one with a pull request, CI checks it, a maintainer reviews it, and it goes live when it's merged.

  1. Get the template

    Download the package template or copy templates/package/ from the repository.

    Rename the folder to your package id: PascalCase letters and digits, for example CertificateTools. The id has to be unique in the catalog.

    • module.psd1: name, one-line description, version, your GitHub username, category, tags and the modules every script needs.
    • Script.ps1: rename it to Verb-Noun.ps1 with an approved verb (Get-Verb). One script is one menu entry. Add as many as you need.
    • _Helpers.ps1 (optional): files starting with _ are shared helpers, not menu entries.
    • Widgets/Widget.ps1 (optional): a home screen widget. Delete the folder if you don't need one.
    • README.md (optional): shown on the package page.

  2. Write your scripts

    • Fill in the $ScriptInfo hashtable with plain values only. The catalog reads it without running your script.
    • Use a normal param() block. OpsKit prompts for mandatory parameters, using HelpMessage as the prompt text and ValidateSet as a pick list.
    • Return objects. OpsKit shows them as a table and offers CSV and JSON export.
    • Use the OpsKit helpers (Read-OpsKitText, Write-OpsKitStatus, Invoke-OpsKitForEach, …) instead of Write-Host, Read-Host or Format-Table.
    • Get-, Test- and Find- scripts must be read-only. Anything that changes something must confirm first with Read-OpsKitConfirm.
    • Widgets must be fast and read-only: no prompts and no sign-ins.

  3. Test it in OpsKit

    Copy the folder into your OpsKit Custom/ folder, restart OpsKit and run every script and widget. Then run the same checks CI runs, from a clone of the catalog repository:

    Install-PSResource PSScriptAnalyzer -Scope CurrentUser
./build/Build-Catalog.ps1 -ValidateOnly

  4. Open a pull request

    Fork the repository, add your folder under packages/ and open a pull request. The pull request template has a short checklist. One package per pull request keeps reviews quick.

    Changing a package later? Bump Version in module.psd1 in the same pull request. OpsKit uses it to offer updates.

  5. Pass the checks

    CI runs on every pull request and posts a summary listing what passed and what failed. The same script builds the site, so a package that passes here will publish.

    CheckWhy
    module.psd1All fields present, a known category, a semantic version. OpsKit and the catalog need them to list and update your package.
    $ScriptInfo / $WidgetInfoPlain values only, so metadata can be read safely without running any code.
    ParsingEvery .ps1 and .psd1 parses without errors.
    PSScriptAnalyzerNo errors or warnings, apart from a short documented list of excluded rules.
    Banned patternsInvoke-Expression, downloading and running code, -EncodedCommand, base64 payloads, turning off security tools, hard-coded secrets, writing to profiles or startup locations, and Set-ExecutionPolicy. These are how malicious scripts usually hide.
    Files and sizeOnly .ps1, .psd1 and .md, at most 256 KB, no binaries. Everything must be readable in review.
    Version bumpIf any file changed, the version must be higher than on main, so OpsKit users get the update.
    catalog.jsonThe generated catalog matches the published schema, so OpsKit can read it.

    If a banned pattern is a false alarm, allow that line with a comment that says why. A maintainer has to approve it.

    # opskit-allow DownloadCode: downloads the vendor's CSV feed, never runs it

  6. Review and publish

    A maintainer reads every line of a new package or a change before merging. After the merge, the site and catalog.json rebuild within a few minutes.
